# 互联网的工作原理

本篇是 TryHackMe Pre Security 学习路径的第五篇笔记，沿着"在浏览器里输入一个网址、按下回车，页面是怎么出现在眼前的"这条主线，依次讲清 DNS 域名解析、HTTP 协议、网页本身的工作原理，最后把所有环节串成一条完整的链路。

## 一、DNS 详解

上一篇文章提到过，DNS 是"把域名翻译成 IP 地址的电话簿"。这一节深入看看它到底怎么工作。

**域名系统（Domain Name System，DNS）**：将人类容易记忆的域名（如 `tryhackme.com`）解析成计算机用于寻址的 IP 地址（如 `104.26.10.229`）的服务（*DNS is a system that turns human-friendly domain names into IP addresses*）。没有它，我们上网就得记 `104.26.10.229` 这种一串数字。

### 1. 域名层级（Domain Hierarchy）

一个域名从右往左，层级越来越高、越来越具体：

```
admin.tryhackme.com
       │            └── .com 顶级域（TLD，Top-Level Domain）
       │                └── tryhackme 二级域（SLD，Second-Level Domain）
       └────────────────── admin 子域（Subdomain）
```

- **顶级域（TLD）**：域名最右边那一部分。分两类：通用顶级域（如 `.com`、`.org`、`.net`）和国家顶级域（如 `.cn`、`.uk`）。
- **二级域（SLD）**：TLD 左边的部分，通常就是网站的"名字"，如 `tryhackme.com` 里的 `tryhackme`。
- **子域（Subdomain）**：二级域左边再加前缀，如 `admin.tryhackme.com` 里的 `admin`。子域可以再嵌套子域（如 `a.b.tryhackme.com`），每一级用 `.` 分隔。

### 2. 记录类型（Record Types）

DNS 服务器里存着多种"记录"，每种回答一类问题：

| 记录类型 | 全称 | 作用 |
|----------|------|------|
| A 记录 | Address Record | 把域名指向一个 IPv4 地址 |
| AAAA 记录 | Address Record | 把域名指向一个 IPv6 地址 |
| CNAME | Canonical Name | 把一个域名"别名"到另一个域名，如把 `blog.example.com` 指向 `example.com` |
| MX | Mail Exchange | 指定该域名的邮件服务器，用于收发电子邮件 |
| TXT | Text Record | 存放任意文本，常用于域名所有权验证、反垃圾邮件的 SPF/DKIM 配置 |
| NS | Name Server | 指定该域名的权威 DNS 服务器（负责最终回答该域名解析请求的服务器） |

### 3. 域名解析的过程（How DNS Resolves a Domain）

当你输入 `tryhackme.com` 并回车：

1. 浏览器先查**本地缓存**——之前查过的解析结果会暂存一段时间，避免每次重复查询。
2. 缓存没有，就向本地配置的 **DNS 解析器（Recursive Resolver）**（通常来自你的路由器或运营商）发起查询。
3. 解析器按层级逐级追问：先问**根服务器**（知道所有 TLD 服务器在哪），再问**TLD 服务器**（知道每个二级域名的权威服务器在哪），最后问**权威服务器**，拿到真正的 IP 地址。
4. 解析器把结果返回给你的设备并缓存下来，按 **TTL（Time To Live）** 决定缓存存活多少秒。

这里涉及一个安全风险：**DNS 劫持/投毒**——如果攻击者能篡改 DNS 应答，就能把域名指向自己的恶意服务器，用户访问"正规网站"时实际连到了攻击者的机器。所以在渗透测试里，检查 DNS 配置是否正确也是一项常见的排查点。

## 二、HTTP 详解

网页要靠浏览器和服务器"对话"才能加载出来，而它们对话用的"共同语言"就是 HTTP。

**超文本传输协议（HyperText Transfer Protocol，HTTP）**：客户端（浏览器）与 Web 服务器之间通信的请求-响应协议（*A request-response protocol between clients and servers*）。当你访问一个网站，浏览器发送 **请求（Request）**，服务器返回 **响应（Response）**。

### 1. HTTP 方法（HTTP Methods）

请求里要告诉服务器"你想干什么"，这就是 HTTP 方法：

| 方法 | 作用 |
|------|------|
| `GET` | 请求获取资源，只读，不改变服务器数据 |
| `POST` | 向服务器提交数据、创建新资源（如表单提交） |
| `PUT` | 整体更新/替换一个资源 |
| `DELETE` | 删除服务器上的指定资源 |

Web 里最常见的操作是 `GET`——浏览器加载一个页面、刷新、点链接，基本都是发 `GET` 请求。

### 2. 状态码（Status Codes）

服务器收到请求后，在响应里用一个三位数**状态码**告诉客户端"处理得怎么样"：

| 状态码 | 含义 |
|--------|------|
| 1xx | 信息性响应（如 100 Continue） |
| 2xx | 成功（200 表示 OK，201 表示已创建） |
| 3xx | 重定向（301 永久移动、302 临时移动，浏览器会自动跳转到新地址） |
| 4xx | 客户端错误（400 请求语法错误、401 未认证、403 禁止访问、404 资源不存在、405 方法不允许） |
| 5xx | 服务器错误（500 服务器内部出错、503 服务不可用） |

### 3. 请求头与响应头（Headers）

HTTP 请求和响应都带有"附加说明"——**头部（Headers）**，以 `键: 值` 的形式告诉对方这次通信的额外信息。常见的请求头有 `Host`（请求哪个域名）、`User-Agent`（什么浏览器/客户端）、`Cookie`（携带会话信息）、`Content-Type`（发送内容类型）；常见的响应头有 `Content-Type`（返回内容类型）、`Set-Cookie`（让浏览器种下 Cookie）、`Location`（配合 3xx 告诉浏览器跳去哪）。

### 4. Cookie 与 HTTPS

**Cookie**：服务器通过 `Set-Cookie` 响应头下发的一小段数据，浏览器保存后，之后的每次请求都会自动带上。它让"无状态"的 HTTP 记住你是谁——登录后保持登录状态、记录购物车，靠的都是 Cookie。在 Web 安全里，盗取 Cookie（如通过 XSS）往往就等同于劫持了会话。

**HTTPS（HTTP Secure）**：HTTP 外面再套一层 **TLS（传输层安全协议）** 加密。这样浏览器与服务器之间传输的内容（包括密码、Cookie）都是密文，中间人即使截获也读不懂。现在主流网站默认都是 HTTPS，访问时如果浏览器提示"不安全"，就要警惕了。

## 三、网站的工作原理

网站本身是由什么构成的？这一节从最基础的三种技术讲起。

### 1. HTML（超文本标记语言）

**HTML（HyperText Markup Language，超文本标记语言）**：定义网页**结构**的语言。它不是编程语言，而是用一对对**标签（Tags）** 把内容"框"起来，告诉浏览器哪块是标题、哪块是段落、哪里放图片。例如：

```html
<h1>网站标题</h1>
<p>这是一个段落。</p>
<a href="https://example.com">点击跳转</a>
<img src="cat.png" alt="一张猫的图片">
```

标签还可以带**属性（Attributes）**，如上面 `href` 指定链接地址、`src` 指定图片来源、`alt` 指定图片的文字替代说明。

### 2. JavaScript（脚本语言）

**JavaScript（JS）**：让网页"动"起来的行为语言。它运行在浏览器里，负责处理点击事件、表单校验、动态更新页面内容、向服务器请求数据（Ajax/fetch）等。HTML 负责"骨架"，CSS 负责"外表"，JavaScript 负责"行为"，三者共同构成一个现代网页。

### 3. 敏感数据暴露（Sensitive Data Exposure）

网站开发中常见的安全隐患之一：开发者不小心把**敏感信息泄露到了前端**——比如在 HTML 源码里写死 API 密钥、数据库密码，或把后台接口地址、内部目录路径暴露在注释、控制台、响应里。攻击者查看网页源码（按 F12）就能把这些"藏起来的秘密"找出来。这也是 Web 安全入门最先学会的"捡漏"手法之一。

> 注：访问任何网站时按 F12 打开开发者工具，在 Elements、Sources、Network、Application 面板里翻一翻，看看能不能发现管理员接口、硬编码凭据等敏感信息——这是练习 Web 渗透的第一步。

### 4. HTML 注入（HTML Injection）

如果网站把用户输入的内容**原样当作 HTML 解析并渲染**到页面上，攻击者就可以"注入"自己的 HTML 标签，篡改页面显示。例如在搜索框输入 `<h1>被黑了</h1>`，页面如果直接把这段显示成标题，就说明存在 HTML 注入。它和后续要学的 XSS（跨站脚本）一脉相承，只是 XSS 注入的是 JavaScript 代码。

## 四、把所有东西整合起来

最后，把前面四篇文章学到的所有环节串成一条完整的链路：当你在浏览器输入 `https://tryhackme.com` 并回车，究竟发生了什么？

1. **DNS 解析**：浏览器先查本地缓存，没有就向 DNS 解析器发起查询，把 `tryhackme.com` 解析成具体的 IP 地址（对应本篇第一节）。
2. **建立连接**：浏览器与服务器的 `443` 端口（HTTPS）建立 TCP 连接，完成三次握手；随后通过 TLS 握手协商加密方式，建立加密通道（对应第四篇与本节 HTTPS）。
3. **发送 HTTP 请求**：浏览器构造一个 `GET /` 请求，带上 `Host`、`User-Agent`、`Cookie` 等头部，发送给服务器（对应本篇第二节）。
4. **服务器处理**：Web 服务器（如 Nginx、Apache）收到请求，可能还要查询数据库、调用后端逻辑，然后生成 HTML 响应。
5. **返回响应**：服务器返回状态码 `200 OK`，正文就是网页的 HTML 代码；如果资源不存在，会返回 `404` 等错误码。
6. **浏览器渲染**：浏览器解析 HTML，遇到其中的 CSS、JavaScript、图片等资源再逐个发起新的请求，最终把整个页面渲染出来（对应本篇第三节）。

整条链路里每一环都可能是攻击者的切入点：DNS 能被劫持、HTTP 能被中间人篡改（所以要 HTTPS）、服务器上的 Web 漏洞能被利用（如注入）。Pre Security 的这几篇笔记，就是为后面理解这些攻击与防御打下的地基。
