# CSRF介绍

## 1. CSRF基础

### 一、什么是CSRF（跨站请求伪造）

**CSRF**（Cross-Site Request Forgery，跨站请求伪造）是一种通过伪造受害者的请求，让服务器误以为是受害者本人的合法操作，从而执行状态变化类操作（如改密码、改邮箱、转账）的攻击方式。

攻击者无法读取受害者的数据，但可以**代替受害者向服务器发送请求**，达到"借刀杀人"的效果。

### 二、CSRF与XSS的区别

| 对比项 | XSS（跨站脚本） | CSRF（跨站请求伪造） |
| --- | --- | --- |
| 攻击目标 | 窃取用户数据 / 篡改页面内容 | 代替用户执行服务器操作 |
| 核心本质 | 在受害者浏览器中**执行脚本** | 在受害者浏览器中**发起请求** |
| 对用户数据 | 可直接读取 | 不可读取，只能"代发" |
| 是否需要执行JS | 需要 | 大多不需要（利用浏览器自动携带Cookie的特性） |

简单总结：**XSS 偷数据，CSRF 干坏事。**

### 三、CSRF攻击流程

CSRF 攻击的完整流程如下：

1. 受害者登录一个合法的网页应用，浏览器存储了会话 Cookie（Session Cookie）。
2. 攻击者诱使受害者访问包含虚构请求（伪造请求）的恶意网页。
3. 受害者的浏览器会自动将请求连同存储的会话 Cookie 一起发送给目标应用程序。
4. 目标应用程序收到请求后，由于 Cookie 有效，误认为是受害者本人的合法操作，从而执行了攻击者想要的状态变化操作。

**核心思路：** 攻击者本人并不持有受害者的 Cookie，但受害者的浏览器会自动把 Cookie 带上——浏览器"替"攻击者完成了携带身份凭据这一步。

### 四、CSRF攻击的关键条件

要使 CSRF 攻击成功，需要同时满足以下三个条件：

1. **受害者必须被认证为目标应用程序。**（否则请求没有身份凭据，服务器不认）
2. **应用程序必须执行状态变化操作**，如更新设置或修改账户数据。（只有状态变化操作才有破坏价值）
3. **应用程序不得核实请求是否来自可信来源。**（服务器只认 Cookie，不验证 Referer、Origin 等来源信息）

### 五、常见的CSRF易受影响特征

以下类型的操作最容易成为 CSRF 攻击的目标（都是状态变化类接口）：

- Change Email Address（修改邮箱）
- Update Account Password（更新账户密码）
- Edit Profile Details（编辑个人资料）
- Alter Payment Info（修改支付信息）
- Updating Payment Info（更新支付信息）
- Submit User Preference Form（提交用户偏好设置表单）

**判断特征：** 只要某个操作是"登录状态 + 修改数据/设置"，且请求头中没有额外的 CSRF 防护标记，就属于 CSRF 高发点。

## 2. CSRF的攻击方式

### 一、GET型CSRF（利用 `<img>` 标签）

如果目标接口使用 GET 方法且不校验来源，攻击者只需在恶意网页中放置一个图片标签，浏览器访问图片 URL 时就会自动发起该 GET 请求：

```html
<img src="http://victim.com/account/change-email?email=attacker@evil.com">
```

受害者浏览恶意页面时，浏览器自动请求该 URL，同时携带受害者的会话 Cookie，成功执行改邮箱操作。

### 二、POST型CSRF（利用自动提交表单）

如果目标接口使用 POST 方法，攻击者可以构造一个自动提交的表单，在页面加载时立即触发：

```html
<form action="http://victim.com/account/change-password" method="POST">
    <input type="hidden" name="newpassword" value="attacker123">
    <input type="hidden" name="confirmpassword" value="attacker123">
</form>
<script>
    document.forms[0].submit();  <!-- 页面一打开就自动提交 -->
</script>
```

受害者的浏览器会自动提交该表单，并携带会话 Cookie，服务器同样无法区分这是否为受害者本人的操作。

### 三、攻击载荷的常见载体

- **恶意网站**：诱导受害者访问攻击者搭建的钓鱼页面。
- **XSS 结合**：若目标站点存在 XSS，可在注入的脚本中发起 CSRF 请求，绕过同源限制。
- **邮件/社交平台**：利用图片外链、链接点击等方式诱导受害者发起请求。

## 3. CSRF Token 防护

### 一、什么是CSRF Token

**CSRF Token**（跨站请求伪造令牌）是服务器生成的一段随机字符串，随表单/页面一起下发给用户，并在用户提交请求时要求一并带回。服务器校验 Token 是否匹配，从而确认请求确实来自本站页面，而不是外部伪造的请求。

**工作原理：**

1. 服务器在页面中下发一个随机的 Token（通常放在隐藏字段里）。
2. 用户提交表单时，浏览器将 Token 一并发送。
3. 服务器比对 Token 是否与当前会话匹配，不匹配则拒绝请求。

**攻击者为什么绕不过：** 攻击者的恶意页面无法获取受害者的 Token（同源策略阻止跨域读取），因此构造的请求中 Token 为空或错误，服务器可以识别并拦截。

### 二、常见防护措施总结

1. **使用 CSRF Token**：在每个状态变化请求中加入服务端校验的随机 Token，最常见且有效。
2. **校验 Referer / Origin 头**：拒绝来自非本站来源的请求。
3. **SameSite Cookie 属性**：将 Cookie 设为 `SameSite`，阻止浏览器在跨站请求时携带 Cookie（见下节）。
4. **二次确认**：对敏感操作（如改密码、转账）要求用户重新输入密码或验证码。
5. **使用自定义请求头**：要求请求携带 `X-Requested-With` 等自定义头，跨站表单无法伪造。

### 三、SameSite Cookie

**SameSite** 是 Cookie 的一个属性，用于控制浏览器在**跨站请求**时是否携带该 Cookie：

| 属性值 | 行为 |
| --- | --- |
| `SameSite=Strict` | 任何跨站请求都不携带 Cookie（最严格） |
| `SameSite=Lax` | 大多数跨站请求不携带，但**顶级导航**（如直接点击链接跳转）会携带 |
| `SameSite=None` | 跨站请求也携带（需要配合 `Secure`，仅限 HTTPS） |

**意义：** 现代浏览器默认将未设置 SameSite 的 Cookie 视为 `Lax`，这已能在很大程度上缓解 GET 型 CSRF，但 POST 型表单提交（跨站表单无法作为顶级导航携带 Lax Cookie）同样被挡住。要注意 `SameSite=None` 会重新放开跨站携带，此时必须依赖 Token 等其他防护。

**判断特征：** 若站点使用 `SameSite=None` 且无 Token 校验，则 CSRF 攻击面最大，属于高优先级测试点。
