# IDOR介绍

## 1. IDOR基础

### 一、什么是IDOR（不安全的直接对象引用）

**IDOR**（Insecure Direct Object Reference，不安全的直接对象引用）是一种**访问控制**漏洞：应用程序直接使用用户可控的标识符（如数据库 ID、文件名、记录编号）来访问对象（数据记录、文件、账户等），却**没有校验当前用户是否有权访问该对象**。

**典型场景：** 登录后访问 `http://victim.com/profile?id=101` 查看自己的资料，把 `id` 改成 `102`、`103`……就能查看**其他用户**的资料。

**一句话概括：** 服务器"信任"用户传来的 ID，却没有核实"这个对象是不是你的"。

### 二、认证（Authentication）与授权（Authorization）的区别

要理解 IDOR，必须先分清这两个概念：

1. **认证（Authentication）：** 确认"你是谁"——验证用户身份（登录、Cookie、Token）。
2. **授权（Authorization）：** 确认"你能干什么"——验证用户是否有权限执行某操作或访问某对象。

**IDOR 的本质是"授权缺失"：** 系统正确完成了认证（用户确实登录了），但**没有做授权检查**——没有验证"该对象是否属于该用户 / 该用户是否有权访问"。

**核心成因：** 应用程序直接引用用户提供的对象标识符，却未在**服务端**执行对象级的权限校验。

### 三、IDOR为什么普遍存在

1. **直接引用内部标识**：数据库自增 ID、文件名、订单号直接暴露在 URL/API 中，且**可预测、可枚举**。
2. **只做了"登录校验"**：很多开发只判断"是否登录"，没有对每个对象做"是否属于你"的二次校验。
3. **过度信任前端**：认为"用户看不到的字段就安全"，实际上攻击者可以随意篡改请求参数。
4. **接口批量暴露**：一次接口返回大量数据（如整个表），过滤只做在前端展示层。

## 2. IDOR的类型

### 一、水平越权（Horizontal Privilege Escalation）

访问**同等级权限**下其他用户的资源。例如普通用户 A 查看、修改普通用户 B 的资料、订单、私信。

```http
GET /api/v1/account/1234   ← 自己的账户
GET /api/v1/account/1235   ← 改成别人的账户，越权查看
```

### 二、垂直越权（Vertical Privilege Escalation）

访问**更高权限**的资源或功能。例如普通用户直接调用管理员的接口、操作管理功能。

```http
GET /admin/delete-user?id=100
```

如果普通用户会话也能访问该接口且未校验角色，就属于垂直越权——访问了本不该属于当前权限等级的**对象/功能**。

### 三、文件引用型IDOR（直接文件引用）

以文件名、路径、编号直接访问文件。攻击者猜测或枚举文件名即可下载任意用户的文件：

```http
GET /download?file=invoice_101.pdf
GET /docs/2026/user_5_annual_report.pdf
```

### 四、对象ID枚举

标识符为连续数字（自增 ID）、可预测编号时，攻击者可以**批量枚举**遍历所有对象，形成大规模数据泄露。即使标识符是 **UUID**（不可猜测），只要 IDOR 存在，通过其它渠道泄露的 UUID 依然可以被越权访问——**随机的 ID 降低风险，但治标不治本**。

## 3. IDOR的常见位置

| 位置 | 示例 | 特征 |
| --- | --- | --- |
| URL 查询参数 | `?id=101`、`?file=report.pdf` | 参数值可替换、可枚举 |
| URL 路径 | `/users/123`、`/api/orders/456` | RESTful 风格，标识符在路径中 |
| POST 请求体 | 表单、JSON 中的 `"user_id": 5` | 隐藏字段、JSON 字段常被忽略校验 |
| Cookie / 请求头 | 会话中携带的对象标识 | 容易被篡改 |
| 文件下载接口 | `?filename=xxx.pdf` | 直接文件引用 |

**判断特征：** 请求中存在**可预测、可枚举的对象标识符**，且该标识符直接对应某个数据对象，就值得测试 IDOR。

## 4. 如何发现和利用IDOR

### 一、利用Burp Suite抓包分析

IDOR 的发现通常依赖**拦截并篡改请求**：

1. 登录普通用户账户，正常执行操作（查看资料、下载文件、删除记录）。
2. 用 Burp Suite 拦截这些请求。
3. 找出请求中的对象标识符（`id`、`user_id`、`file`、`uuid`、`order` 等）。
4. 修改标识符的值为**另一个用户/另一个对象**的值，观察响应。

### 二、篡改ID的测试方法

```http
# 原始请求（自己的账户）
GET /account/1234

# 测试1：改成相邻 ID，看是否越权访问他人
GET /account/1235

# 测试2：改成管理员 ID，测试垂直越权
GET /account/1

# 测试3：HTTP 方法替换（GET→POST/PUT/DELETE），测试隐藏的操作接口
PUT /account/1234   # 尝试直接改别人的资料
```

### 三、枚举与自动化

- 对连续数字 ID 编写脚本（Burp Intruder / 脚本）批量遍历。
- 观察响应长度、状态码、返回数据的差异来筛选越权成功的请求。
- 在 API 文档、JS 文件中寻找接口路径与参数，扩大测试面。

### 四、IDOR利用的完整流程

1. 注册 / 登录两个以上的用户（用户A、用户B），便于交叉验证越权。
2. 以用户 A 身份抓取请求，定位对象标识符。
3. 把标识符改成用户 B 的对象，确认能否访问/修改。
4. 尝试横向（同权限其他用户）与纵向（更高权限）两种越权。
5. 若可修改、删除，进一步确认数据破坏能力；结合批量枚举评估泄露规模。

## 5. IDOR的危害

| 危害场景 | 后果 |
| --- | --- |
| 水平越权读数据 | 窃取其他用户的个人隐私（PII）、聊天记录、订单、医疗等敏感数据 |
| 水平越权改数据 | 篡改他人资料、删除他人记录、冒充他人下单/转账 |
| 垂直越权 | 普通用户执行管理员操作，直接接管系统 |
| 批量枚举 | 遍历所有对象 ID，造成大规模数据泄露 |
| 账户接管 | 结合改密码、重置流程等接口，可能进一步接管他人账户 |

## 6. IDOR防护措施

1. **服务端对象级授权**：每次访问对象时，在服务端校验"当前用户对该对象是否有权限"，**绝不只在前端隐藏按钮**。
2. **不直接暴露内部标识**：用随机的、不可枚举的标识符（UUID）替代自增 ID；敏感文件用随机文件名/临时下载令牌。
3. **最小权限与访问控制列表**：基于用户、角色建立对象级别的访问控制（如"本人/群组/所有人"）。
4. **对接口做权限分层**：区分普通用户接口与管理员接口，并校验角色；管理接口必须独立鉴权。
5. **请求参数服务端校验**：以**会话中的用户身份**为准获取对象，而不是信任请求体里传的 `user_id`。
6. **日志与监控**：记录异常的对象访问（如越权尝试、批量枚举），及时告警。

**判断特征：** IDOR 的根治在于**把"对象归属校验"从业务代码的每一处访问点落实**，而不是简单把 ID 换成 UUID——否则泄露的 UUID 依然能被越权利用。

## 7. IDOR与相关概念对比

| 对比项 | IDOR | 未授权访问 | 垂直越权 | 水平越权 |
| --- | --- | --- | --- | --- |
| 核心 | 对象级授权缺失 | 功能级授权缺失 | 访问更高权限对象/功能 | 访问同级他人的对象 |
| 是否需登录 | 需要（已认证但未授权） | 不一定 | 需要 | 需要 |
| 表现 | 改 ID 就能看到别人的数据 | 未登录直接访问受保护页面 | 普通用户调用管理接口 | 用户A访问用户B数据 |

**总结：** IDOR 是访问控制类漏洞中最常见的一种——**认证通过不等于授权通过**。测试时抓住"对象标识符是否可控 + 是否做了服务端校验"这两个要点即可，利用时配合 Burp 抓包、篡改标识符、批量枚举三步走。
