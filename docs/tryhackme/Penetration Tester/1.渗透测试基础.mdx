# Guided Pentest: Web

## 任务一：端口扫描

端口扫描：`nmap -sV -sC -p- ip`

HTTP响应头获取：`curl -I ip`

目录枚举：`feroxbuster -u http://ip -w /usr/share/wordlists/dirb/big.txt -x php,html,txt,bak,zip -t 50 --depth 2`

通过端口扫描、响应头获取、目录枚举后，我们可以得到目标的基础信息。

## 任务二：什么是IDOR？

IDOR的全称是**不安全的直接对象引用**。它的核心问题是：应用程序在访问数据（如数据库记录、文件等）时，直接使用了用户提供的对象标识符（比如一个ID号），但没有验证当前用户是否有权限访问该标识符对应的数据。

一个最常见的例子是，一个用户登录后，通过访问 `https://example.com/profile?user_id=123` 查看自己的资料。如果攻击者将URL中的`user_id`改成`124`，就能看到另一个用户的资料，那么这里就存在IDOR漏洞。

## 任务三：弱密码重置

弱密码重置漏洞，是指网站或APP的"密码重置"功能在逻辑设计上存在缺陷，导致攻击者可以利用这些缺陷，未经授权篡改他人账户的密码。

它和IDOR关系非常密切——IDOR是导致弱密码重置漏洞最常见的技术原因之一。简单来说，**IDOR是攻击手法，密码重置漏洞是攻击结果**。

这类漏洞通常表现为以下几种典型场景：

1. **参数IDOR篡改（最常见）**：后端通过URL或请求体中的`user_id`、`username`来识别要重置谁，但未校验该参数是否属于当前操作者。攻击者只需修改这个ID，就能重置任意用户密码。

2. **重置凭证可预测/被窃取**：系统向邮箱或手机发送的验证码（或URL链接Token）太简单（如4位纯数字），且未限制输错次数，可被暴力破解；或者Token直接等于时间戳、用户名的MD5，攻击者可自行生成。

3. **验证步骤逻辑跳过**：前端页面仅通过"隐藏"或"灰色不可点"来控制步骤，但后端未校验当前进度。攻击者可直接访问重置成功的接口，跳过短信/邮箱验证环节。

4. **绑定数据未绑定会话**：在"输入验证码 -> 设置新密码"这一步，后端只验证了验证码是否正确，却没有验证这个验证码是发给谁的。攻击者用自己手机号获取验证码，输入后，将请求中的用户ID改为目标受害者，即可修改对方密码（这也是IDOR的一种）。

### 与IDOR的直接联系

结合你上一个问题，它们的联系是：

- **IDOR是"矛"**：通过篡改`user_id`等资源标识符，绕过前端展示限制。
- **弱密码重置是"靶子"**：重置功能恰好接受了这个被篡改的ID，且缺乏绑定校验，导致越权发生。

例如，攻击者抓取重置密码的包，将`{"user_id":1001, "new_password":"123456"}`改为`{"user_id":1002, "new_password":"123456"}`——此时IDOR（改ID）触发了越权（改了别人的密码），这整个过程就是一次典型的弱密码重置漏洞利用。
